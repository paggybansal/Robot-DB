Day 1: Domain Vocabulary & Concepts

To successfully operate and extend the Provider Data Quality Automation (PDQA) framework, you must possess a robust understanding of the healthcare provider credentialing domain. This automation does not simply click UI elements; it maps, validates, and asserts complex data states representing actual clinical and billing networks.

What is a Provider?

In healthcare, a "Provider" can be an individual person or an organization. In our system, these entities are explicitly divided into Practitioners, Practices, and Facilities. Each carries unique regulatory structures and database dependencies.

The Three Core Entities

1. Practitioner

A Practitioner is an individual healthcare professional licensed to deliver clinical services (e.g., Doctors of Medicine (MD), Doctor of Osteopathic Medicine (DO), Advanced Practice Registered Nurses (APRN), Audiologists).

  • Identifiers: Individually identified by a 10-digit Type-1 NPI (National Provider Identifier) and a 9-digit Social Security Number (SSN).
  • Credentialing Rules: Must be linked to at least one primary specialty and must have active licensing before insurance products can be attached.

2. Practice (Group / Clinic Network)

A Practice represents a business entity or corporate group under which practitioners operate (e.g., "Advocate Radiation Oncology" or "University of Maryland St. Joseph Medical Group").

  • Identifiers: Identified by an organizational 10-digit Type-2 NPI (Group NPI) and a corporate 9-digit Tax ID Number (TIN).
  • Role in Ingestion: Practices act as the corporate parent. Practitioners must establish a valid relation to a Practice before they can be scheduled or billed.

3. Facility

A Facility is the physical location, building, or hospital institution where care is delivered (e.g., "Phoenix VAMC" or "Aiswarya Fertility Clinic").

  • Identifiers: Identified by a Type-2 NPI, a Tax ID, and specialized Facility Type classifications (e.g., Behavioral Clinic, Urgent Care Center, Freestanding Emergency Room).
  • Role in Ingestion: Facilities are strictly bound to location compliance. Their service addresses must be validated against USPS address guidelines before products can be linked.

Relational Data Entities

The Primary Location Constraint

A Practitioner can operate out of multiple locations within a Practice network (e.g., Dr. Smith works at the Waveland office on Mondays, and the Biloxi office on Tuesdays). However, to safeguard billing and contract enrollment, the system demands that exactly **one** location be explicitly marked as the Primary Location (PrimaryLocation = 'Y'). Product/insurance agreements are strictly bound to this primary location; attempting to link a product to a non-primary location triggers a fatal business rule rejection.

Healthcare data enforces a strict separation of concerns for addresses. A single clinic entity requires three distinct address definitions:

Unified Address Mapping Models

A major technical hurdle we overcame was a mapping mismatch between the Postgres/GoRules API engine and our Flat CSV bulk-upload template. GoRules evaluates three distinct address blocks, but our flat CSV structure historically only supported two (Billing and Service).

The "Tax ID" Address Mapping Solution

To populate and test the third node (address.taxIDAddress) without modifying the downstream legacy CSV parsers, we designed a mapping override. When we need to load a Tax ID Address, we populate the Billing Address Columns in the CSV, but we set the column value `BillingAddressTypeName` strictly to `"Tax ID"`. The loader reads this and routes it into the database as a Tax ID address, triggering the corresponding GoRules node.

Day 2: GoRules Parsing & Integration

Day 2 introduces the business rules engine: **GoRules**. We'll cover how our framework handles rule processing, timing phases, and automatic data correction checks.

What is the GoRules Service?

GoRules is a containerized business rules engine that intercepts our transformed payloads and runs validation checks on them. The results are logged as a structured JSON object in Postgres. Our framework flattens and validates these results in real time.

GoRules Response Payload Structure

The GoRules response JSON contains a "rules" block divided into entity sections. Here is an authentic payload example showing both standard runs and triggered errors:

{
  "data": {
    "nationalProviderID": "1114619954",
    "lastName": "kumar",
    "firstName": "sunil"
  },
  "rules": {
    "speciality": [
      {
        "ruleID": "BRP_0053",
        "ruleName": "MissingPrimarySpecialityCheck",
        "messageType": "Success",
        "message": ""
      },
      {
        "ruleID": "BRP_0054",
        "ruleName": "MultiplePrimarySpecialityCheck",
        "messageType": "Error",
        "message": "MULTIPLE PRIMARY SPECIALTIES"
      }
    ],
    "practice.serviceLocation.product": [
      {
        "ruleID": "BRP_0023",
        "ruleName": "ProductOnNonPrimaryLocation",
        "messageType": "Error",
        "message": "Non-primary location should not have product/contracts assigned"
      }
    ]
  }
}

GoRules Validation Logic (Flattening Algorithm)

Because rules are scattered across different sections in the JSON (`speciality`, `practice.serviceLocation.product`, etc.), the framework uses a flattening algorithm to verify them uniformly:

def _flatten_go_rules(response_json: dict) -> List[dict]:
    """
    Flattens GoRules sections (speciality, demographics, products, etc.)
    into a single list of rules, injecting the source section as metadata.
    """
    rules_obj = response_json.get("rules", response_json) or {}
    flat_list = []
    
    for section_name, section_rules in rules_obj.items():
        if isinstance(section_rules, list):
            for rule in section_rules:
                rule_copy = dict(rule)
                rule_copy["_section"] = section_name
                flat_list.append(rule_copy)
                
    return flat_list

Real-Life Test Scenarios

This section provides a complete, step-by-step guide to testing the 8 most critical BRP, BRG, and BRF business rules in our automation suite, including actual input data and database tracing queries.

Scenario 1: BRP_0023 — ProductOnNonPrimaryLocation

Business Context: A practitioner can work at multiple clinics within a practice group, but insurance contracts are strictly tied to their **Primary Location** (the location where the provider spends most of their time). To maintain data integrity, you cannot attach an insurance product to a secondary, non-primary location.

Input Payload setup: Set PrimaryLocation = 'N' for the Service Location, but still attach a product contract (e.g. EP1000261) under the same location block.

{
  "NationalProviderID": "1114619954",
  "ServiceLocationname": "LEXINGTON CLINIC",
  "PrimaryLocation": "N",              // ❌ Set to non-primary
  "ServiceLineNumber1": "1221 S Broadway",
  "ProductName": "A001 - Non Par Network",
  "ProductContractName": "A001",       // ❌ Try to link product here
  "ProductStatusTypeName": "Non-Participating"
}

DB Verification Query: Verify that the practitioner location record was successfully created as non-primary in SQL Server, and that the product loading step was correctly blocked:

SELECT 
    ploc.PractitionerLocationRecID,
    ploc.PrimaryLocation, -- Expected: 'N'
    (SELECT COUNT(1) FROM LocationProducts lp WHERE lp.LocationID = ploc.LocationID) AS ProductCount -- Expected: 0 (blocked)
FROM PractitionerLocations ploc
JOIN Practitioners pr ON pr.PractitionerID = ploc.PractitionerID
WHERE pr.NationalProviderID = '1114619954';

Scenario 2: BRP_0027 — ProductSpecialtyPresentInDemogSpecialtyCheck

Business Context: Before you can enroll a provider in an insurance network with a specific contract specialty (e.g., Cardiology), the provider must actually hold that specialty at their high-level demographic credentialing level. You cannot link a product specialty to a provider who isn't credentialed for it.

Input Payload setup: Define a product specialty (e.g., Cardiology), but leave the high-level practitioner specialties completely blank.

{
  "NationalProviderID": "1114619954",
  "ProductSpecialtyName": "Cardiology", // ❌ Product specialty provided
  "PractitionerSpecialtyName": ""       // ❌ High-level specialty left blank
}

DB Verification Query: Verify that no high-level specialty was created for this practitioner, causing the product creation step to be skipped:

SELECT 
    (SELECT COUNT(1) FROM PractitionerSpecialties ps WHERE ps.PractitionerID = p.PractitionerID) AS DemogSpecialtyCount, -- Expected: 0
    (SELECT COUNT(1) FROM LocationProducts lp JOIN PractitionerLocations pl ON pl.LocationID = lp.LocationID WHERE pl.PractitionerID = p.PractitionerID) AS ProductCount -- Expected: 0
FROM Practitioners p
WHERE p.NationalProviderID = '1114619954';

Scenario 3: BRG_0004 — PracticeTypeServCatCheck

Business Context: Enforces consistency between the Practice Type (e.g., `"Primary Care"`, `"Specialist"`, `"Solo Association"`) and the specialties offered. A clinic designated as `"Primary Care"` cannot have an advanced, whitelisted specialist category like `"Cardiology Services"` assigned to its locations.

Input Payload setup: Upload a practice update setting `PracticeTypeName` to `"Primary Care"`, but specify `'CARDIOLOGY SERVICES'` (case-sensitive) as the location's service category name.

{
  "GroupNationalProviderID": "1770836785",
  "PracticeTypeName": "Primary Care",                      // ❌ Primary Care
  "BillingAddressTypeName": "Billing",
  "BillingServiceTypeName": "Group Specialty",
  "BillingServiceCategoryTypeName": "CARDIOLOGY SERVICES"   // ❌ Specialist category
}

DB Verification Query: Verify that the practice location is classified as a Billing location, but has an incompatible service category mapping:

SELECT 
    pl.LocationName,
    pl.LocationTypeName, -- Expected: 'Billing'
    ls.ServiceCategoryTypeName -- Expected: 'CARDIOLOGY SERVICES'
FROM vwPracticeLocations pl
JOIN vwLocationServices ls ON ls.LocationID = pl.LocationID
WHERE pl.PracticeNationalProviderID = '1770836785';

Scenario 4: BRG_0003 — GroupSpecServCatCheck

Business Context: Broad clinical departments must align with compatible specialties. For example, you cannot map a service department designated as `"Dentistry"` to an active specialty category of `"Cardiology"` or `"Dermatology"`.

Input Payload setup: Set `BillingServiceTypeName` to `"Dentistry"` and map it to `BillingServiceCategoryTypeName` of `"Cardiology"`.

{
  "GroupNationalProviderID": "1770836785",
  "BillingServiceTypeName": "Dentistry",             // ❌ Dental Department
  "BillingServiceCategoryTypeName": "Cardiology"      // ❌ Medical Specialty
}

DB Verification Query: Verify that the location's service category mappings contain the mismatch, causing the transaction to fail:

SELECT 
    ls.ServiceTypeName,         -- Expected: 'Dentistry'
    ls.ServiceCategoryTypeName  -- Expected: 'Cardiology'
FROM vwLocationServices ls
JOIN vwPracticeLocations pl ON pl.LocationID = ls.LocationID
WHERE pl.PracticeNationalProviderID = '1770836785';

Scenario 5: BRP_0022 — MultiplePrimaryLocations

Business Context: A single practitioner cannot be assigned more than one active primary location within the same practice/group. Having multiple primary locations would break scheduling systems and contract assignments.

Input Payload setup (Two-row CSV upload): Create a single CSV with two rows for the same practitioner NPI and group TIN. Mark `PrimaryLocation = Y` on **both** rows for different addresses.

// Row 1
{
  "NationalProviderID": "1114882784",
  "ServiceLocationname": "Location One",
  "PrimaryLocation": "Y",
  "ServiceLineNumber1": "977 N Collier Blvd"
}
// Row 2
{
  "NationalProviderID": "1114882784",
  "ServiceLocationname": "Location Two",
  "PrimaryLocation": "Y",
  "ServiceLineNumber1": "221 Jericho Tpke"
}

DB Verification Query: Run the developer's query grouped by practitioner ID to verify that more than one active, unarchived primary location is recorded in SQL Server:

SELECT 
    ploc.PractitionerID,
    COUNT(ploc.LocationID) AS PrimaryLocationCount -- Expected: > 1
FROM PractitionerLocations ploc
WHERE ploc.PrimaryLocation = 'Y'
  AND ploc.Archived = 'N'
GROUP BY ploc.PractitionerID
HAVING COUNT(ploc.LocationID) > 1;

Scenario 6: BRP_0021 — MissingPrimaryLocation

Business Context: Conversely, every active practitioner associated with a group must have **at least one** active primary location. You cannot load active locations without designating one as the primary.

Input Payload setup: Upload a new practitioner with an active service location, but set `PrimaryLocation = N`.

{
  "NationalProviderID": "1114882784",
  "ServiceLocationname": "Lexington Clinic",
  "PrimaryLocation": "N",              // ❌ Set to non-primary
  "ServiceLineNumber1": "1221 S Broadway"
}

DB Verification Query: Verify that active service locations exist for this practitioner, but none are marked as primary:

SELECT 
    COUNT(LocationID) AS ActiveLocations,                  -- Expected: > 0
    SUM(CASE WHEN PrimaryLocation = 'Y' THEN 1 ELSE 0 END) AS PrimaryCount -- Expected: 0
FROM PractitionerLocations
WHERE PractitionerID = (SELECT PractitionerID FROM Practitioners WHERE NationalProviderID = '1114882784')
  AND Archived = 'N';

Scenario 7: BRP_0058 — MissingSpecialityCheckNonPAR

Business Context: Non-Participating (Non-PAR) practitioners do not belong to the standard provider network and typically do not require the same clinical credentialing checks. However, to maintain basic directories, they **must still have at least one valid specialty** mapped in the database.

Input Payload setup: Map a product with `ProductStatusTypeName` set to `"Non-Participating"`, but leave all high-level practitioner specialty fields completely blank.

{
  "NationalProviderID": "1114882784",
  "ProductStatusTypeName": "Non-Participating",
  "PractitionerSpecialtyName": ""       // ❌ Missing specialty
}

DB Verification Query: Verify that the provider is loaded without active specialties and with only non-participating products, which triggers the error:

SELECT 
    (SELECT COUNT(1) FROM PractitionerSpecialties WHERE PractitionerID = p.PractitionerID AND Archived = 'N') AS SpecialtyCount, -- Expected: 0
    (SELECT COUNT(1) FROM vwPractitionerProducts WHERE PractitionerID = p.PractitionerID AND StatusTypeName = 'Participating') AS ActiveProductCount -- Expected: 0
FROM Practitioners p
WHERE p.NationalProviderID = '1114882784';

Scenario 8: BRF_0005 — FacilityAddressCheck

Business Context: Physical locations (Facilities) must have accurate address records. Zip codes must match standard formats: exactly **5 digits** (e.g. `60602`) or **9 digits** (e.g. `60602-1234`). Bad zip codes (such as those containing letters or wrong lengths) must trigger failures across **all three address nodes**: Billing, Service, and Tax ID.

Input Payload setup: Provide invalid zip codes (`12`, `34`, `56`) across the Billing, Service, and Tax ID address blocks in the CSV. (To test the Tax ID block, we use the `Billing...` columns but set `BillingAddressTypeName` to `"Tax ID"`).

{
  "FacilityID": "65605336",
  "BillingZipCode": "12",               // ❌ Invalid Billing Zip
  "BillingAddressTypeName": "Billing",
  "ServiceZipCode": "34",               // ❌ Invalid Service Zip
  "ServiceAddressTypeName": "Service"
}

DB Verification Query: Verify that the addresses are saved with invalid zip formats, triggering the errors across both nodes:

SELECT 
    LocationName,
    LocationTypeName, -- Matches 'Billing' and 'Service'
    ZipCode           -- Expected: '12' and '34' (invalid formats)
FROM vwPracticeLocations
WHERE PracticeNationalProviderID = '1396510228';

Day 2: Debugging Failed Executions

This section is a practical playbook for debugging failed runs in your automation pipeline. If an automated script fails, use these steps to diagnose the issue quickly.

Playbook Step 1: Check for System Crashes in Postgres

Before checking GoRules or database records, check if the validation service crashed during processing. In Postgres, run this query:

SELECT 
    id, sub_process_name, status, error, created_at
FROM process_status
WHERE process_id = '9d28bec9-f335-425e-91af-3ee63ffd68c0' -- Replace with your Tracking No / Process ID
ORDER BY created_at ASC;

What to look for: If any row has a status of Error, check the error column. For example, if it says 'NoneType' object has no attribute 'lower', this is a system crash (typically due to a missing mandatory field like specialty name) and should be reported to the development team as a bug.

Playbook Step 2: Fetch Raw GoRules Output

If the pipeline completed successfully but your rules didn't fire as expected, run this query to retrieve the exact rules output from GoRules:

SELECT jsonb_pretty(response::jsonb -> 'rules')
FROM payload_response
WHERE payload_response_id = 55088843; -- Replace with the GoRules payload_response_id

What to look for: Examine the array of evaluated rules. Look for your target rule name (e.g. `ProductOnNonPrimaryLocation`). If it has a `messageType` of `Success`, it means the data you uploaded was actually valid, and you need to adjust your overrides to trigger the error condition.

Playbook Step 3: Check Actual Saved DB State

If GoRules reported an error but your test didn't fail, or vice versa, check the actual state of the record in the Symplr database:

SELECT 
    pr.NationalProviderID,
    ploc.PrimaryLocation,
    ploc.DateTo,
    ploc.Archived
FROM Practitioners pr
JOIN PractitionerLocations ploc ON ploc.PractitionerID = pr.PractitionerID
WHERE pr.NationalProviderID = '1114619954'; -- Replace NPI

What to look for: Check if PrimaryLocation is saved as Y or N. If it is N but your input CSV had Y, it means your CSV generation script is overwriting your overrides, or there is an existing primary location in the database causing a conflict.

Day 2: Extending the Automation Suite

One of the main strengths of the PDQA framework is how easy it is to extend. This section shows how to add new rules to your test suite.

Adding a New Rule in 3 Steps

Step 1: Add the Rule Metadata to the Catalog

Open `pdqa_db_validation.py` and add your new rule to `GO_RULES_CATALOG` or `GROUP_GO_RULES_CATALOG`:

# Adding a new practitioner rule
"BRP_0099": {
    "ruleName": "NewRuleCheck",
    "phase": 2,
    "entity": "Practitioner Location",
    "error_type": "Error",
    "auto_correct": "N",
    "timing": "Both",
    "message": "Expected rule failure message",
}

Step 2: Add a Database Query for Test Data (For Negative Tests)

Open `pdqa_db_queries.py` and write a query to fetch valid test data candidates:

def get_new_rule_violation_data() -> dict:
